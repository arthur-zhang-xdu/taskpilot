## 2. 已确定的项目方向

项目名称：**TaskPilot：可评测的研发故障分析 Agent**。

典型任务：

> 分析 payment-service 在指定 30 天内的故障，统计最常见的三类问题，检索相关排障文档，生成带有数据依据和来源引用的 Markdown 报告。缺少证据时明确说明，不执行实际修复。

第一版支持：故障查询与统计、排障知识检索、综合分析报告。

核心闭环：自然语言任务 → 受限工具调用 → 数据统计与知识检索 → 结构化报告 → 结果验证 → 执行轨迹 → 独立评测。

注意：故障记录与文档通常只能支持可能原因和排查建议，不能直接证明真实根因。报告应区分事实、推测和待验证事项。

### 技术决策

- Python、FastAPI、Pydantic。
- 先用简单执行循环跑通，再引入 LangGraph；不在 Day 1 学完或搭完框架。
- 后续采用 PostgreSQL、SQLAlchemy、Alembic、pgvector。
- 外部 LLM API 与 Embedding API；模型供应商尚未确定。
- 后续采用 Streamlit、pytest、HTTPX、Docker Compose、可用的 CI 平台。
- 前期单任务、低并发；先验证可靠性。
- 查询与统计由代码执行，不让模型心算，不开放任意 SQL。
- Agent 与评测器分离，基准答案不能直接复用被测函数而形成自证。
- 后续优先采用结构化报告加 Markdown 模板，便于确定性检查。

### 暂缓范围

不在第一版加入多 Agent、长期记忆、模型微调、MCP 服务端、任意 Shell 工具、真实服务器修复、完整 Vue 前端、Kubernetes。

### 总体时间安排

- 第 1 周：最小工具调用链路、模拟数据、基础 Trace。
- 第 2 周：RAG、带引用报告、任务 API 与单 Worker。
- 第 3 周：状态控制、异常恢复、独立评测与 50 条案例。
- 第 4 周：实验对比、界面、容器部署，形成可展示版本。
- 第 5 周：补缺、失败分析、文档、演示视频、简历和面试准备。

计划目标并非已有成果：50 条评测任务，35 条开发集、15 条保留集；正常任务成功率争取达到 85% 以上，实际必须按实测报告。

## 6. 建议执行顺序与细节

### A. 环境检查

先检查再安装，读取仓库中适用的 `AGENTS.md` 等说明，不覆盖已有文件或配置。

建议收集：操作系统、CPU、内存、磁盘、当前用户、Python/Git/Docker/Compose 版本、Docker 可用权限、项目目录与 Git 状态。

示例只读命令（按环境选择，不要求原样全部执行）：

```bash
pwd

cat /etc/os-release
uname -m
nproc

```

Docker 未安装不妨碍当天 Python 开发。系统包安装、权限变更及可能影响现有服务的操作先确认必要性，遵循当前会话权限规则，不擅自删除或重置环境。

### B. 最小 Python 环境

- 使用项目独立虚拟环境，优先复用现有合理的环境管理方案。
- Python 3.11+ 是计划基线；先检查现有版本，不为追求最新版本做无关升级。
- Day 1 只安装实际需要的少量依赖，记录版本。
- 标准库足以完成数据生成和统计；API SDK 依据选定供应商确定。
- 检查 `.gitignore`，避免提交 `.env`、虚拟环境、密钥与不必要的运行日志。
- 如需 Git 提交，按用户已有指示与环境权限处理，不自动推送远端。

### C. 模型 API 冒烟调用

先确认已有供应商和账号；没有时只询问完成验证必需的信息。不擅自购买、充值或假定某个平台支持某项能力。

建议通过环境变量传入：

```text
LLM_API_KEY=
LLM_BASE_URL=
LLM_MODEL=
```

变量仅为项目内部建议，不代表所有供应商采用相同协议。按实际 SDK 和官方文档实现。API、价格和版本相关事实需核实当前官方资料。

冒烟脚本应做到：

- 发送一条简短请求并获得非空响应。
- 设置超时和较小输出上限；避免 SDK 隐式重试造成意外重复消耗。
- 记录请求是否成功、模型名称、耗时、可获得的 Token 用量。
- 不打印 Key、Authorization 头、完整环境变量或敏感原始异常。
- 未返回 Token 用量时标记未知，不填假数据。
- Day 1 普通文本调用成功即可；工具调用能力可以额外验证，但不是当天完成前提。

没有 Key 或遇到网络问题时，数据工作继续；Mock 调用必须注明，不能作为真实 API 验收证据。

### D. 模拟故障数据

建议使用 JSONL，先避免引入数据库学习成本。

每条记录至少包含：

```json
{
  "incident_id": "inc_0001",
  "service": "payment-service",
  "occurred_at": "2026-10-01T09:30:00+08:00",
  "error_type": "connection_timeout",
  "severity": "P2",
  "message": "模拟：连接上游服务超时",
  "resolution": "模拟处理记录：检查连接池与上游延迟"
}
```

约束：

- 100 条记录，ID 唯一，明确标注为合成数据。
- 3 个左右服务，4–6 种错误类型，使用受控且非均匀的分布。
- 固定随机种子和固定时间范围，不使用不断变化的当前时间生成基准。
- 日期带时区，项目展示默认 Asia/Shanghai。
- 同一参数生成的内容一致。
- 不编造真实事故、客户、生产指标或公司内部数据。

### E. 查询与统计

实现函数或 CLI：按服务、开始时间、结束时间过滤，再按错误类型计数并输出 Top K。

统一规则：

- 时间区间采用 `[start_time, end_time)`。
- 按数量降序，数量相同按错误类型名称升序，保证可复现。
- Top K 默认 3；不足 3 类则返回实际类别数。
- 百分比的分母是过滤后的故障总数。
- 空数据输出总数 0 与空列表，不除以零、不生成虚构结论。
- 无效时间或开始时间不早于结束时间，给出明确错误。
- 不使用 LLM 完成统计。

验证使用一份独立手写的 6–10 条小样本，预先写明预期结果，检查服务过滤、起止边界、并列计数与空结果。不要仅调用同一个统计函数两次作为验证。

当天只需适量、能发现错误的测试，不为简单实现堆砌测试数量。
